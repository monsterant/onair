# onair 리뷰 규칙 (2026-11-09 사용자 결정)

이슈 구현을 시작할 때 읽고, 이 규칙대로 계획·구현·확인한다. Claude가 혼자 짜고 혼자 확인하면 자기 실수를 못 볼 수 있어서,
따로 띄운 에이전트가 이슈·계획과 코드를 대조하게 한다.

## 1. PR 종류 정하기

| 종류 | 기준 | 예 |
|---|---|---|
| 기능 PR | 서버나 화면의 동작이 바뀐다 | API, DB 구조, 인증·권한, 방송 상태, 송출·시청, 결제 |
| 작은 PR | 동작이 바뀌지 않는다 | 문서, CI, 오타, 동작이 같은 정리 |

- 애매하면 기능 PR로 본다.
- 설정 변경도 서버 동작이 바뀌면(포트, 권한, 미디어 서버 설정 등) 기능 PR이다.
- CLAUDE.md의 "작은 수정"은 **이슈 없이 PR을 올려도 되는지**를 정하고, 이 표는 **리뷰를 얼마나 무겁게 할지**를 정한다. 둘은 따로 본다.
  - 예: 승인된 이슈 범위 안의 버그 수정은 이슈 없이 PR을 올려도 된다. 하지만 동작이 바뀌므로 기능 PR 리뷰를 한다.

## 2. 기능 PR 흐름

사용자가 말한 "3단 검증"은 두 뜻을 모두 가진다(2026-11-09 사용자 확인).
- 세 **단계**: 단계 리뷰(3) → 3관점 리뷰 + 검증자(4) → 공격적 재검토(5)
- 세 **관점**: 4번의 요구사항 · 정확성 · 보안·권한

```
계획 → 구현(단계별) → 단계 리뷰 → 3관점 리뷰 + 검증 → 공격적 재검토
   → 확정 지적은 재수정 이슈로 기록하고 고친다 → (바뀐 곳 다시 리뷰, 최대 2바퀴) → 보고서 → PR
```

1. **계획:** `my-notes/plans/<yyyy-MM-dd>-<이슈>-계획-<제목>.md`
   - 이슈 체크리스트를 단계로 나눈다.
   - 단계마다 완료 조건과 테스트를 적는다.
2. **구현:** 단계마다 커밋한다. 테스트를 먼저 쓰거나 함께 쓴다.
3. **단계 리뷰 (에이전트 1개, 단계마다):**
   - 이 단계가 이슈·계획대로인지 본다.
   - 빠진 것, 계획에 없는 것이 섞였는지 본다.
   - 코드 품질을 본다.
4. **3관점 리뷰 (에이전트 3개를 동시에) + 검증자 (에이전트 1개):**

   | 관점 | 보는 것 |
   |---|---|
   | 요구사항 | 이슈 체크리스트와 공모 요구사항을 모두 채웠는지, 빠진 것 |
   | 정확성 | 예외 처리, 경계값, 동시성(두 요청이 동시에 올 때), 방송 상태가 꼬이는 경우 |
   | 보안·권한 | 인증, 방송 소유자 검사, 비밀값 노출, 입력 검증 |

   - 검증자는 각 지적을 코드나 실행 결과로 확인한다.
   - 확인 결과는 `확정` / `가능성` / `기각` 셋 중 하나로 매긴다.
   - `가능성`은 재현을 한 번 더 시도한다. 그래도 확인이 안 되면 고치지 않고 "남은 지적"으로 보고서와 PR에 적는다.
5. **공격적 재검토 (에이전트 2개를 동시에):**
   - A. 동작 사냥: "어딘가 틀렸다"고 가정하고, 이슈·계획과 다르게 동작하는 곳과 이상한 입력에 깨지는 곳을 찾는다.
   - B. 변이 시험: 코드를 일부러 망가뜨려 테스트가 잡는지 본다. 못 잡으면 테스트가 약한 것이다.
     - 반드시 따로 떼어 낸 작업 사본(worktree)에서 하고, 끝나면 버린다.
6. **확정 지적 처리 (재수정):**
   - 한 바퀴의 확정 지적을 이슈 1개로 묶어 기록한다.
     - 제목: `[재수정] #<원래 이슈> <요약>`
     - 라벨: `재수정`
     - 본문: 지적마다 체크 칸 1개
   - 재수정 이슈는 **승인을 기다리지 않고** 바로 같은 브랜치에서 고친다(2026-11-09 사용자 지시: "다시 이슈 만들어서 재수정하는 과정까지 진행"). 고친 지적은 체크한다. PR 본문에 `Closes #<재수정 이슈>`를 적는다.
   - 이 PR 범위를 벗어나는 큰 문제는 CLAUDE.md의 `[나중]` 이슈(`나중에` 라벨)로 기록하고 넘긴다. 다만 필수 요구사항, 보안, 돈 문제는 넘기지 않고 바로 보고한다.
7. **다시 리뷰:** 고친 부분을 중심으로 4·5를 다시 돌린다.
   - 바퀴 수 = 4·5를 도는 횟수다. 첫 리뷰가 1바퀴, 고친 뒤 다시 리뷰가 2바퀴다. **최대 2바퀴**까지 돈다.
   - 2바퀴째는 1바퀴에서 확정 지적이 나온 관점만 다시 돌린다(전부 다시 돌리지 않는다).
   - 그 뒤에도 남은 지적은 보고서와 PR에 "남은 지적"으로 적는다.
8. **보고서:** `my-notes/reviews/<yyyy-MM-dd>-<이슈>-리뷰-<제목>.md`
   - 무엇을 고쳤는지 적는다.
   - 지적과 판정, 재수정 이슈 링크를 적는다.
   - 남은 지적을 적는다.
   - PR 본문에는 요약을 싣는다.
9. **CI 통과**는 필수다.
10. **승인 요청:** Slack 알림으로 PR 링크와 남은 지적 수를 보낸다(2026-11-09 사용자 지시: 승인이 필요하면 Slack으로 알림).
    - 웹훅 주소는 비밀값이라 저장소에 두지 않는다. 이 PC의 저장소 밖 파일에서 읽는다(위치도 저장소에 적지 않는다).
    - 알림은 알리기만 한다. 승인은 사용자가 터미널에서 답하거나 PR을 머지하는 것이다.

## 3. 작은 PR 흐름

1. CI 통과
2. 리뷰 에이전트 1개가 확인한다.
   - PR이 이슈·설명과 맞는지 본다.
   - 실수(오타, 깨진 링크, 비밀값)가 있는지 본다.
3. 지적은 바로 고친다. 재수정 이슈는 만들지 않는다.

## 4. 에이전트 규칙

- 리뷰 에이전트에게는 이슈, 계획, 코드(diff), 공모 원문(`my-notes/2026-11-09-공모요구사항-실시간방송플랫폼.md`)만 준다. Claude의 결론이나 "잘 됐다"는 판단은 주지 않는다.
  - 이유: 결론을 주면 리뷰어가 그 결론에 끌려가서, 같은 실수를 놓친다.
- 리뷰 에이전트는 읽기만 한다. 코드 수정, 커밋, push를 하지 않는다. 예외는 5-B 변이 시험의 작업 사본뿐이다.
- 근거(파일:줄, 실제 코드, 실행 결과)가 없는 지적은 받지 않는다.
- 지시문은 저장소 밖에 둔 리뷰어·검증자·공격적 재검토 지시문을 바탕으로 쓴다.
  - 다른 프로젝트(Java·Spring) 전용 항목(애노테이션, 트랜잭션 애노테이션, 팀 commit 스킬)은 Rust·onair에 맞게 바꿔 쓴다.
  - 예: 애노테이션 대신 `async`, 에러 처리(`Result`), sqlx 트랜잭션을 본다.
- 비용 상한 (기능 PR 1개 기준):
  | 단계 | 에이전트 수 |
  |---|---|
  | 단계 리뷰 | 계획 단계 수만큼 (단계는 5개 이하로 나눈다) |
  | 1바퀴 (3관점 + 검증자 + 공격적 2개) | 6개 |
  | 2바퀴 (지적이 나온 관점만) | 최대 6개 |
  | **합계** | **최대 17개** |
  - 넘을 것 같으면 PR을 나누거나, 먼저 Slack으로 보고하고 승인받는다.

## 5. pstack과 함께 쓰기 (2026-11-09 사용자 결정)

pstack(Cursor의 `cursor/plugins` 저장소, MIT)을 onair 폴더에만 설치했다(`--scope local`). 바탕은 이 문서의 규칙이고, pstack은 골라서 쓴다.

### 기능 PR은 두 번 만들고 더 나은 쪽을 고른다
1. **1차: onair 방식.** 위 2절 흐름(계획 → 구현 → 단계 리뷰 → 3관점 리뷰 + 검증자 → 공격적 재검토)으로 만든다. 브랜치: `<종류>/<이슈>-<설명>`
2. **2차: poteto-mode.** 같은 이슈를 `/pstack:poteto-mode`(feature, bug-fix, refactoring 플레이북)로 따로 만든다.
   - 1차 결과를 보지 않도록 별도 작업 사본(worktree)과 브랜치에서 만든다. 브랜치: `<종류>/<이슈>-<설명>-poteto`
3. **비교하고 고른다 (Claude가 판단).**
   - 기준: 이슈·공모 요구사항 충족 → 테스트(개수보다 실제로 동작을 지키는지) → 리뷰 확정 지적 수 → 코드 양(적을수록 좋음) → 읽기 쉬움
   - 고른 쪽만 PR로 올린다. 다른 쪽에서 더 나은 부분이 있으면 가져와 합치고 출처를 적는다.
   - 2차 결과물도 1차와 같은 2절 리뷰(3관점 + 공격적 재검토)를 거친 뒤에 비교한다. 리뷰 없이 비교하지 않는다.
   - 비교 표와 고른 이유는 보고서와 PR 본문에 적는다.
4. 작은 PR은 두 번 만들지 않는다(3절 그대로).

### pstack에서 가져다 쓰는 원칙
| 원칙 | onair에서 |
|---|---|
| prove-it-works | "컴파일됨"으로 끝내지 않는다. 송출·시청은 실제 브라우저와 휴대폰으로 확인한다 |
| test-behavior-not-implementation | 사용자가 보는 동작(권한 거절, 방송 상태)을 테스트한다 |
| make-operations-idempotent | 같은 요청이 두 번 와도 결과가 같게 (도네이션 중복 적립 방지 등) |
| boundary-discipline | 검사는 API 입력·외부 응답 같은 경계에 모은다 |
| sequence-verifiable-units | 계획 단계를 작게 나누고 하나씩 확인한다 |

### pstack에서 쓰지 않는 것 (onair 규칙과 부딪힘)
| pstack | 이유 |
|---|---|
| autopilot-full, shipping 플레이북 (PR 머지까지 함) | 머지는 사용자가 한다 |
| never-block-on-the-human 원칙 중 "승인 없이 진행" | 이슈 묶음 승인, 공모 밖 기능 보고, 돈 드는 일 보고는 그대로 지킨다 |
| `/pstack:setup-pstack` | `~/.claude/rules/`에 파일을 써서 다른 프로젝트를 포함한 모든 프로젝트에 영향을 준다 |
| Cursor 전용 기능 (Bugbot, Automations, grok 모델) | Claude Code에 없다. 지금 세션 모델로 대신한다 |

### 정말 모르겠을 때
- 1차와 2차 중 어느 쪽이 나은지 근거를 대고 고를 수 없을 때는 Slack 알림으로 묻는다.
- 이슈·공모 요구사항만으로 정할 수 없는 선택일 때도 Slack 알림으로 묻는다.
- 그 밖에는 Claude가 정하고 보고서에 이유를 적는다.
- 비용 상한(4절)은 1차와 2차 각각에 적용한다. 그래서 기능 PR 1개에 에이전트가 최대 34개까지 쓰인다.
